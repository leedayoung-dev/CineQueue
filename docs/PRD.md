# CineQueue PRD

사용자의 거주 지역과 선호 좌석을 반영하고, 동일 좌석의 동시 요청을 단일 선점으로 제어하며, 매진 시 대기 순서와 결제 제한 시간을 적용하는 영화 예매 웹 서비스의 제품 요구사항입니다.

## 1. 문서 목적

본 문서는 CineQueue의 범위, 업무 규칙, 시스템 구성, 수용 기준을 정의합니다. 구현과 검증은 아래 다섯 가지 목표를 기준으로 완료 여부를 판단합니다.

| ID | 목표 | 완료 기준 |
| --- | --- | --- |
| 3-1 | 개인 맞춤 예매 | 가입 시 거주 지역·선호 좌석 저장, 해당 정보 기반 상영관·좌석 추천 |
| 3-2 | 동시성 제어 | 동일 좌석 동시 선택 시 선점 1건, 확정 예매 1건 |
| 3-3 | 매진 대기열 | 예매 가능 좌석 부재 시 순차 등록, 발생 순서에 따른 예매 기회 부여 |
| 3-4 | 제한 시간 예매 | 제한 시간 내 미결제 시 선점 해제, 다음 대기자에게 기회 이관 |
| 3-5 | 부하 검증 | 동시 100명 예매 시나리오에서 중복 예매 0건 및 응답 시간 측정 |

## 2. 대상 사용자와 범위

회원만 예매할 수 있습니다. 비회원 예매, 관리자 화면, 실결제, 모바일 앱은 본 버전에 포함하지 않습니다.

**포함 범위**

- 회원가입, 로그인
- 거주 지역 기반 상영관 추천, 선호 좌석 표시
- 상영 선택, 좌석 배치도, 선점, 모의 결제, 예매 내역
- 매진 대기열, 대기 순번 조회
- 선점·결제 제한 시간, 만료 시 다음 순번 승격
- Docker Compose 기동, k6 부하 테스트, 동시성 통합 테스트

**제외 범위**

- 실 PG 연동, 환불, 결제 완료 후 취소
- 클라우드 배포, 다중 인스턴스 클러스터, 동시 1만 명 규모
- 외부 영화 API, 예고편, 리뷰, 포인트

영화, 상영관, 좌석, 상영 일정은 시드 데이터로 구성합니다.

실행 환경은 로컬 Docker Compose를 기준으로 합니다. 목표 동시 접속 100명은 API, MySQL, Redis를 함께 기동한 구성에서 재현할 수 있으며, 시연과 부하 테스트를 동일 환경에서 반복할 수 있습니다.

## 3. 업무 규칙

회원가입 시 아래 항목을 필수로 수집합니다.

- 이메일, 비밀번호, 이름
- 거주 지역: 시/도, 시/군/구
- 선호 좌석: 구역(앞 / 중간 / 뒤), 위치(통로 / 중앙)

홈 화면에는 회원과 동일한 시/군/구의 상영관을 우선 노출합니다. 동일 시/군/구에 상영관이 없으면 동일 시/도의 상영관을 노출합니다. 좌석 배치도에서는 선호 조건과 일치하는 좌석을 추천 좌석으로 표시합니다. 추천 좌석이 모두 선점 또는 판매 상태이면, 같은 구역의 잔여 좌석을 이어서 표시합니다.

좌석 상태는 아래 순서로 전이합니다.

`AVAILABLE` → `HOLD` → `SOLD`

`HOLD` 상태에서 결제 전 취소 또는 제한 시간 초과가 발생하면 `AVAILABLE`로 복귀합니다. `SOLD`는 본 버전에서 되돌리지 않습니다.

선점 유지 시간과 대기열 예매 가능 시간은 각각 3분입니다. 두 값은 `application.yml`에서 변경합니다. 시연과 부하 테스트에서 만료 동작을 확인하기 위한 기본값입니다.

매진은 해당 상영의 `AVAILABLE` 좌석이 0인 상태입니다. `HOLD` 좌석만 남은 경우에도 신규 선택은 불가하며, 대기 등록만 가능합니다.

대기열은 상영 단위의 FIFO입니다. 동일 사용자는 한 상영에 한 번만 대기할 수 있습니다. 좌석이 반환되면 선두 사용자에게 3분의 예매 가능 시간을 부여합니다. 해당 사용자가 선점 후 결제를 완료하면 좌석은 `SOLD`가 되고, 대기 항목은 종료됩니다. 예매 가능 시간이 종료되거나 선점 후 결제가 완료되지 않으면 자격을 회수하고, 다음 대기자에게 예매 가능 시간을 부여합니다.

## 4. 사용자 흐름

**일반 예매**

1. 로그인 후 추천 상영관에서 상영을 선택합니다.
2. 좌석 배치도에서 추천 좌석을 확인한 뒤 좌석 1개를 선택합니다.
3. 선점에 성공하면 잔여 시간 3분이 표시된 모의 결제 화면으로 이동합니다.
4. 결제가 성공하면 좌석은 `SOLD`가 되고, 예매 내역에 표시됩니다.
5. 제한 시간을 초과하거나 사용자가 취소하면 좌석 선점을 해제합니다.

**동시 선택**

동일 상영의 동일 좌석에 대한 선점 요청이 겹치면, 하나의 요청만 `HOLD`를 획득합니다. 나머지 요청에는 선점 실패를 반환하고, 좌석 배치도의 상태를 갱신합니다.

**매진 대기**

1. 예매 가능 좌석이 없으면 대기 등록을 제공합니다.
2. 대기 화면에서 본인의 순번을 조회합니다.
3. 선행 사용자의 선점이 해제되거나 결제 제한 시간이 종료되면, 다음 사용자에게 예매 가능 시간을 부여합니다.
4. 예매 가능 시간이 유효한 동안에만 좌석 선택과 결제를 허용합니다.

## 6. 도메인 모델

| 엔티티 | 주요 속성 |
| --- | --- |
| User | email, passwordHash, name, sido, sigungu, seatZone, seatPosition |
| Theater | name, sido, sigungu |
| Screen | theaterId, name, rows, cols |
| Movie | title, runningTime |
| Screening | movieId, screenId, startsAt |
| ScreeningSeat | screeningId + seatId (기본 키), status, holdUserId, holdExpiresAt, version |
| Reservation | userId, screeningSeatId, status, expiresAt, confirmedAt |
| WaitEntry | screeningId, userId, position, status, offerExpiresAt |

`ScreeningSeat`는 상영별 좌석 1행입니다. 상태 변경은 해당 행의 `version`으로 제어합니다.

`Reservation.status`는 `HOLD`, `CONFIRMED`, `EXPIRED`, `CANCELED`를 사용합니다. `WaitEntry.status`는 `WAITING`, `OFFERED`, `CONSUMED`, `EXPIRED`를 사용합니다.

## 7. 동시성 제어

좌석 선점은 아래 두 단계로 처리합니다.

1. **Redis 분산 락.** 키는 `seat:{screeningId}:{seatId}`입니다. 동일 좌석에 대한 요청을 직렬화합니다.
2. **DB 낙관적 잠금.** `ScreeningSeat.version`을 사용합니다. 상태가 `AVAILABLE`인 경우에만 `HOLD`로 변경합니다. 갱신 건수가 0이면 선점 실패로 처리합니다.

확정 예매는 상영·좌석 조합당 `CONFIRMED` 예약 1건을 유지합니다. 상태 전이와 조회 조건으로 이를 보장하고, 통합 테스트에서 중복 0건을 확인합니다.

만료 처리는 1초 주기의 스케줄러가 수행합니다.

- `holdExpiresAt`이 경과한 `HOLD`는 `AVAILABLE`로 복귀하고, 예약 상태는 `EXPIRED`로 변경합니다.
- `offerExpiresAt`이 경과한 대기 제안은 `EXPIRED`로 변경합니다.
- 반환된 좌석이 있고 대기자가 존재하면, 선두 대기자에게 `OFFERED`를 부여합니다.

비즈니스 상태 전이는 Redis 키 만료 이벤트에 연결하지 않습니다. 스케줄러가 DB의 만료 시각을 기준으로 처리하므로, 프로세스 재시작 이후에도 만료 처리를 이어갈 수 있습니다.

대기 순서는 Redis Sorted Set `queue:{screeningId}`에 등록 시각을 점수로 저장합니다. 동일한 순번을 DB `WaitEntry`에도 기록하여, 재시작 후 순서를 복구합니다.

## 8. API

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| POST | `/api/auth/signup` | 지역·선호 좌석 포함 가입 |
| POST | `/api/auth/login` | JWT 발급 |
| GET | `/api/theaters/recommended` | 거주 지역 기준 상영관 조회 |
| GET | `/api/screenings/{id}/seats` | 좌석 배치도·추천 좌석 조회 |
| POST | `/api/screenings/{id}/seats/{seatId}/hold` | 좌석 선점, 대기 차례 필요 시 제안 토큰 검증 |
| POST | `/api/reservations/{id}/pay` | 모의 결제 확정 |
| DELETE | `/api/reservations/{id}` | 결제 전 취소 |
| POST | `/api/screenings/{id}/queue` | 매진 시 대기 등록 |
| GET | `/api/screenings/{id}/queue/me` | 본인 순번, 제안 만료 시각 조회 |

선점 API와 결제 API는 인증된 사용자만 호출할 수 있습니다. 선점 요청은 멱등 키를 수용하며, 동일 사용자의 재시도를 하나의 선점으로 처리합니다.

## 10. 부하 테스트

목표 부하는 동시 사용자 100명, API 단일 인스턴스입니다.

| 시나리오 | 수행 방식 | 통과 기준 |
| --- | --- | --- |
| 동일 좌석 경쟁 | 100 VU, 동일 좌석 동시 선점 | 성공 1건, 나머지 409, 확정 가능 상태 1건 |
| 좌석 분할 선점 | 100 VU, 잔여 좌석 분할 선점 | 성공 수 = 잔여 좌석 수, 중복 예매 0건 |
| 결제 만료 승격 | 선점 후 미결제, 대기자 N명 | 제한 시간 경과 후 순번대로 `OFFERED` 1명씩 부여 |
| 대기 순서 | 순차 등록 후 좌석 1석 반환 | 등록 순서와 제안 순서 일치 |

수집 지표는 선점 API p95, 오류 비율, 중복 `CONFIRMED` 건수, 대기 제안 순서 위반 건수입니다. 로컬 기준선은 선점 API p95 500ms 이하, 중복 예매 0건입니다. 기준선을 초과하면 튜닝 대상으로 기록하고, 기능 결함과 구분하여 관리합니다.

k6 스크립트는 `loadtest/`에 두고, 시드가 완료된 Compose 환경에서 실행합니다.

## 11. 수용 기준

- 가입 응답과 회원 정보에 시/도, 시/군/구, 선호 구역, 선호 위치가 포함됩니다.
- 동일 시/군/구의 상영관이 홈 상단에 노출됩니다.
- 선호 조건과 일치하는 좌석에 추천 표시가 적용됩니다.
- 동시 선점 테스트에서 성공 응답은 1건입니다.
- 매진 상영은 대기 등록만 허용합니다.
- 대기 제안은 등록 시각의 오름차순을 유지합니다.
- 결제 완료 전 제한 시간이 경과하면 좌석은 `AVAILABLE`로 복귀하고, 다음 대기자가 제안을 수신합니다.
- 모의 결제 성공 이후에만 `SOLD`와 `CONFIRMED`로 전이합니다.
- Testcontainers 동시성 테스트와 k6 결과가 제10절의 통과 기준을 충족합니다.

## 13. 제약과 전제

스케줄러 주기는 1초입니다. 만료 반영은 최대 약 1초 지연될 수 있습니다. 수용 기준은 제한 시간 경과 후 다음 대기자에게 제안을 부여하는 것이며, 만료 시각과 동일한 밀리초 일치를 요구하지 않습니다.

본 버전의 배포 단위는 API 단일 인스턴스입니다. Redis 분산 락은 인스턴스 수를 늘리는 경우에도 좌석 단위 직렬화를 유지하기 위해 적용합니다. 이번 부하 목표는 동시 100명입니다.

클라이언트의 잔여 시간은 서버가 반환한 `expiresAt`을 기준으로 계산합니다. 브라우저 로컬 시계와 서버 시각의 차이를 이 값으로 흡수합니다.
